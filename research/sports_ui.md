## 1. 各サービスの画面構成の要約

### 1-1. スポーツナビ(スポナビ野球速報アプリ)

公式サポートによる試合詳細ページの構成は **タブ5枚**。

| タブ | 中身 |
|---|---|
| トップ | 予告先発、スタメン、戦評 |
| 速報 | リアルタイム更新される「今の1球」 |
| 経過 | 時系列の全プレー(テキスト) |
| 成績 | 出場選手の打者・投手成績 |
| 応援 | 応援コメント |

- タブ間は**上部メニュー or 左右スワイプ**で移動。片手・親指前提。
- 速報ページは「ランナー図表 / 配球チャート / ポジション図 / 条件別成績 / 投球・打撃データ」の**複数ビジュアルの積み重ね**。
- **ボールアイコンの色分けが秀逸**: 黄=ストライク、緑=ボール、赤=アウト、青=出塁、橙=犠打。球種は図形(形)で識別。
  → **色=結果、形=球種**という二重エンコード。色覚に依らず読める。
- 各要素は「試合前 / 試合中 / 試合後」で**表示内容そのものが差し替わる**(フェーズ別UI)。
- 2023年アップデートで速報画面に投球・打撃データを追加。「テレビを見ながら1球ごとの球種・球速・配球も確認できる」ことを訴求 = **セカンドスクリーン前提の設計**。

### 1-2. MLB Gameday (MLB.com)

- **ヘッダーが常時スコアバグ**: スコア / カウント / アウト数 / 走者の塁上状況 を1か所に固定。スクロールしても消えない。
- 投球はすべて**色分け+ホバーで球種・球速・軌道・位置**。Pitch-f/x(現Statcast)由来のリアルデータ。
- 「Live scoreboard」セクションが**試合の一瞬要約(score / inning / count / runners)**を担い、その下に詳細が続く二層構造。
- Gameday 3D は投球軌道・打球軌道・野手位置・**走者の走路**まで3D再現し、カメラを360度動かせる。
- 過去には「Gameday Mini」という**極小ウィンドウ版**が存在。最小構成で何を残すかの良い教材(スコア・カウント・走者だけ)。

### 1-3. ESPN(アプリ / Gamecast)

- **暗い背景 + 明るいグレーのカード**で Live Games を浮かせる。カードそのものが階層を作る。
- ロゴとスコアを最も大きく = 「どっちが勝っているか」を最優先。
- ただし**批判もある**: お気に入り設定をしていても興味のない競技をスクロールで通過させられる。
  → 教訓: **並び順の優先度は、ユーザーの関心に合わせて動的に変えないと階層が機能しない**。
- Win Probability(勝利確率)を試合ページに統合。「65%→30%に落ちた」という表現は、どんな形容詞よりも**その一球の重大さ**を伝える。Excitement Index(勝率変動の絶対値の総和)で試合の盛り上がりを1数値化する手法もある。

### 1-4. NPB+ (プロ野球速報アプリ)

App Store レビューから読める**失敗パターン**が有益。

- 「速報が飛ぶ」= **状態の連続性が切れる**と観戦感が壊れる。
- 「空振り三振の表示が分かりにくい」= 結果イベントの視覚差が弱い。
- 「ストライクゾーンの枠が見にくい」「配球図の球種表示が不明確」= 図の線の太さ・コントラスト不足。
- 「投球が大きく逸れるとスコア表示の裏に隠れる」= **レイヤーの衝突**。オーバーレイと図が同じ座標を奪い合っている。
- 「プレーが終わると詳細データにアクセスできない」= **履歴に戻れない**。

出典: https://apps.apple.com/jp/app/npb/id6746151454

### 1-6. スポーツ中継のテロップ設計(放送グラフィック)

- 野球中継のテロップは、トータルスコア/ボールカウント/スピードガン/ストライクゾーン投球図が**標準装備**化。2Dから3Dへ、さらに**「音連動」(動きに合わせてSEが鳴る)**テロップへ。
- 出す情報は3系統に整理できる:
  1. **恒常情報**(スコアバグ) — 常に出ている
  2. **紹介テロップ** — 選手名・背番号・ポジション・打率などを打席入りで出し、数秒で消える
  3. **記録・ハイライトテロップ** — 達成時に大きく出て、画面を占有する
- 専用テロッパーは事前にチーム/選手データを登録し、**ワンボタンで送出**する設計。=「出す判断」と「作る作業」を分離している。

### 1-7. スコアバグのデザイン論(Sports Video Group / 2026)

現代のスコアバグ設計で語られている論点(検索結果より):

- **可読性はサイズではなく、コントラスト・書体設計・字間・階層・モーション・抑制の総合**。
- 「バーで見ていて読めるか?」が実務上の合格ライン。85インチTV、スマホ、空港のモニタ、圧縮された配信、**そのすべてで生き残る**必要がある。
- → 本ゲームでも同じ: **375px幅で読めるか**が唯一の合格ライン。

出典: https://www.sportsvideo.org/2026/06/09/designing-the-modern-scorebug-how-broadcast-graphics-teams-are-rethinking-the-most-important-element-on-screen/

### 1-8. 「野球のスコアボードは最高のUI」論(note / さかいさとみ)

本ゲームの課題に最も直接効く一本。

- スコアボードは **得点 > イニング・カウント・走者 > その他** という優先順位が物理的に固定されている。
- 情報は**消すのではなく「主役 / 判断材料 / 補足」の3層に分類**する。分類さえ決まれば文字サイズと配置は自動的に決まる。
- 「全部目立たせて」は**「全部目立たない」と同義**。同じサイズで複数が主張すると、ユーザーは「どこを見ればいいか分からない」状態に陥る。
- 解決策は**変化した箇所だけを視覚的に変える**こと。同じ役割のパーツには一貫した色・形・位置を使う。

出典: https://note.com/amotdesign/n/n5b8f495a7321

### 1-9. データテーブルのモバイル設計(順位表・成績表向け)

- **1列目を固定(sticky)** して横スクロールしても識別子(チーム名/選手名)が消えないようにする。ヘッダー固定と同格に重要。合計列など右端も固定する場合あり。
- モバイルでは**列を絞る / 1行=1ミニカードにスタックする / 横スクロール+固定ヘッダー**の3択。
- 数字は**tabular numerals(等幅数字)**で桁を縦に揃える。
- 明るい色は**本当に重要なシグナルにだけ**取っておく。

出典:
- https://www.pencilandpaper.io/articles/ux-pattern-analysis-enterprise-data-tables
- https://medium.com/design-bootcamp/designing-user-friendly-data-tables-for-mobile-devices-c470c82403ad
- https://www.mobilespoon.net/2019/11/design-ui-tables-20-rules-guide.html

### 1-10. 野球シミュレーションゲームの提示手法(OOTP / Diamond Mind)

- OOTPは **One-Pitch Mode / Pitch-by-Pitch Mode** の2段階。One-Pitchでは打席ごとに戦略選択だけして、**決着した最後の1球だけを表示**する。
  → **「全球見せる」と「打席単位で見せる」は排他ではなく、ユーザーが選ぶ設定**にできる。
- OOTP 26 では 3D play-by-play、pitch-by-pitch操作、**動的リアルタイムスコアボード**をテキストエンジンに重ねて没入感を作っている。
- Diamond Mind は**テキストの記述そのものの濃さ**で没入を作っている系譜。

出典:

## 2. 現状コードの所見(提案の前提)

- `game.js` L2426 `renderDiamond()` に**ダイヤモンド図はすでに存在**する(3塁ベースの点灯 + アウトの●3つ + 打者/投手名)。
  - ただし `#lv-sit` に描かれ、**ログの上に置かれた静的ブロック**。スクロールしない代わりに、スコア(ラインスコア)とは離れている。
  - **カウント(B-S-O のB/S)が存在しない**。シミュレーションが打席単位(`simOutcome`)で、投球単位のイベントを持たないため。
- ログ `#lv-pbp` は `half / chg / end / hit / run / hr` の6クラスで色分け済み。HRだけ朱色の帯。**強弱は既にあるが、階層が浅い**。
- ラインスコアは9イニング+R。**H(安打)・E(失策)列がない**。
- 進行は `setInterval(liveStep, liveMs())` の**等間隔**。全イベントが同じ重み・同じ間隔で流れる = 山場が作れない。
- 成績表 `.stat-t` は既に `position:sticky` の1列目・ヘッダー、`font-variant-numeric:tabular-nums` を実装済み(良好)。`min-width:560px` の横スクロール型。

## 3. 私たちのゲーム画面への改善案 20

> ①何をするか ②なぜ見やすく/楽しくなるか ③実装難易度(小/中/大)

### ① B-S-Oカウント表示を新設し、打席を「投球単位」に分解する

① `simOutcome` の結果キーから**逆算して配球シーケンスを生成**する(K→最低3球、BB→4球、安打→1〜5球目でヒット、等)。生成した投球を `{ball, strike}` の遷移列として `pa` イベントの中に持たせ、ダイヤモンド図の横に **B ●●● / S ●● / O ●●** の3段ランプを置く。実際のカウント遷移は「投球ごとに1つ点灯 → 打席終了でリセット」。スポナビの色分け(黄=ストライク、緑=ボール、赤=アウト)をそのまま採用する。
② 現状は「打席の結果だけ」が文字で流れるため、**打席の途中という時間が存在しない**。カウントがあると「2-3、フルカウント」という緊張が生まれ、次の1行を待つ理由ができる。これが「試合を見ている感」の中核。MLB Gameday もスポナビもヘッダーの必須要素として持っている。
③ **中**(シミュレーション本体は変えず、結果キーから配球列を後付け生成するだけ。描画はCSSの丸3種)

### ② ダイヤモンド図+カウントを「スコアバグ」に統合し、パネル上部に常時固定する

① 現在バラバラの `#lv-board`(ラインスコア)・`#lv-sit`(ダイヤモンド)を、上から **[チーム名/スコア] → [イニング + BSO + ダイヤモンド]** の1ブロックにまとめ、`position:sticky; top:0` でパネル最上部に貼り付ける。ログだけがスクロールする。
② MLB Gameday のヘッダー、ESPNのスコアバグと同じ構造。**「今なにが起きているか」が1か所に集まる**ので視線が往復しない。375px では特に効く。
③ **小**(既存要素の並べ替え + sticky指定)

### ③ 走者の塁間アニメーション(トゥイーン)と、生還時のホームベース点灯

① 走者ドットを塁のdivではなく**絶対座標のドット**として持ち、打席結果の前後で `transform: translate()` を CSS transition (200〜400ms) で補間する。ホームに到達したドットは、ホームベースを一瞬フラッシュさせてから消える。
② 現状は塁が「点いた/消えた」の離散変化で、**誰がどこから還ったのかが見えない**。動きがあるだけで「見ている」感覚が桁違いになる。Gameday 3D が走者の走路まで描くのはこのため。`simOutcome` は既に `scored[]`(誰が還ったか)を返しているので、データは揃っている。
③ **中**(座標計算とtransition。走者の同一性を `bases` 配列から追跡する必要あり)

### ④ 打球方向インジケーター(ダイヤモンド上に打球のアークを一瞬描く)

① `DIR_1B / DIR_2B / DIR_HR / DIR_GO / DIR_FO / DIR_LN` の文字列を**方向ベクトルにマッピング**し(例: 「レフト前」→左45度・短、「バックスクリーン」→中央・場外)、ダイヤモンド上に打球の軌跡をSVGパスで 500ms だけ描いて消す。ゴロは低く短い直線、フライは高い弧、本塁打はスタンドまで抜ける。
② 「レフト前」というテキストを読む前に、**目が先に方向を理解する**。テキストログとビジュアルが同じ情報を二重にエンコードするので、速いスピード設定でも取り残されない。既存の方向定数を再利用するだけで、新しいデータは不要。
③ **中**(方向テーブルの作成 + SVGアニメ)

### ⑤ ラインスコアに H(安打)・E(失策)列を追加し、得点したセルを点灯させる

① `<th>R</th>` の後ろに `H` `E` を追加。イベント側で安打(`1B/2B/3B/HR`)と失策(`E`)をカウント。さらに、そのイニングで得点が入った瞬間に該当セルを **朱色→琥珀に1秒フラッシュ**させる。
② R-H-E は野球中継の**世界共通のフォーマット**で、あるだけで本物らしくなる。セルのフラッシュは「変化した箇所だけを視覚的に変える」というスコアボードUI論の原則そのもの。今どこが動いたのかが一目で分かる。
③ **小**(集計はイベントループ内で加算するだけ)

### ⑥ 本塁打・タイムリー時の「フルバンドテロップ」演出

① `cls === "hr"` および `runs >= 2` のイベントで、ログ行を出す前に**画面幅いっぱいの帯テロップ**を 1.2秒オーバーレイ表示する。中身は「本塁打 / 選手名 / ソロ・2ラン・満塁 / 推定飛距離」を明朝体+朱色の印判で。左からワイプイン、右へワイプアウト。既存の `noiseBurst`(歓声SE)と同期させる。
② 現状HRは「ログの中の朱色の1行」でしかなく、**淡々と流れていく**。放送のテロップは「画面を占有する」ことで重大さを表現する。ゲームの世界観(新聞紙面風の印判)とも噛み合い、他アプリにない固有の見せ場になる。
③ **小〜中**(オーバーレイdiv + CSS keyframes。SEは既存関数を流用)

### ⑦ 実況ログを3階層に整理し、「重要なプレーだけ」フィルタを付ける

① 各 `pa` イベントに `weight: 0|1|2`(0=凡打・三振、1=出塁・進塁、2=得点・本塁打・失策・サヨナラ)を付与。weight 0 は文字小さめ・低コントラスト、1 は標準、2 は太字+背景色。ログ上部に **[全部/要点だけ]** のトグルを置き、要点モードでは weight≧1 のみ表示。
② 「情報を消すのではなく、主役/判断材料/補足に分類する」というスコアボードUI論の実装。現状は6クラスあるが**視覚的な強弱が3段階に整理されていない**ため、目が全行を等しく読もうとして疲れる。トグルは、2周目以降のプレイで飛ばし読みしたいユーザーを救う。
③ **小**(クラス付与とCSSの調整、トグル1個)

### ⑧ 進行速度を「可変ウェイト」にして、山場で意図的に遅くする

① 現在の `setInterval(liveStep, liveMs())` を `setTimeout` の再帰に置き換え、イベントごとに待ち時間を変える。凡打 = 基準の0.6倍、出塁 = 1.0倍、得点 = 1.6倍、本塁打・サヨナラ = 2.4倍、イニング切り替え = 1.3倍。さらに9回で1点差以下なら全体を1.4倍に。
② 等間隔は**メトロノーム**であって中継ではない。放送は重大な場面ほど「間」を取る。同じ情報量でも、間があるだけで緊張と余韻が生まれる。実装コストの割に体感の変化が最も大きい提案。
③ **小**(setInterval → 再帰setTimeout への置換のみ)

### ⑨ 打席入り時の「選手紹介スーパー」(打者カードを2秒だけ出す)

① 打者が変わるタイミングで、ダイヤモンド図の下に **背番号 / 打順 / 名前 / 打率・本塁打・打点(キャリアハイ値)** を1行スーパーで出し、2秒後にフェードアウト。投手交代時は投手版(防御率・勝敗・S/H)。
② 放送の紹介テロップの再現。**選手が「誰か」が分かると打席に感情移入できる**。本ゲームはドラフトで自分が指名した選手が出てくるので、ここの効果が特に大きい。既に `players.js` に成績があるのでデータ取得コストはゼロ。
③ **小**(既存 `renderDiamond` の隣に1ブロック追加)

### ⑩ イニング切り替え・投手交代の「トランジション」を作る

① `half` イベントで、ログに1行足すのではなく **「▼ 5回表 ○○の攻撃」を画面中央に0.8秒フルスクリーンで出してから**ログに落とす。投手交代 `chg` は「投手交代」の印判スタンプが押される演出(既存の朱色印判デザインを流用)。
② 現状はイニングの境目が**ログ内の色違いの1行**でしかなく、試合の区切りが体感できない。区切りが立つと「もう5回か」という時間感覚が生まれ、9イニングが長い1本の物語になる。
③ **小**(オーバーレイ + CSS)

### ⑪ 球音・歓声SEの拡充と、状況連動

① 既存の `tone()` / `noiseBurst()` を拡張し、**ストライク=短いミット音、ファウル=小さい木の音、安打=カーンという打撃音、本塁打=打撃音+歓声クレッシェンド、三振=どよめき、得点=歓声**を割り当てる。走者ありの場面では常に低いざわめきのループを薄く鳴らす。
② 放送グラフィックの「音連動テロップ」の思想。**視覚と聴覚が同時に来ると"起きた"という実感が生まれる**。特にざわめきループは、無音の間を「球場にいる時間」に変える効果が大きい。既にWeb Audioの土台があるので追加は容易。
③ **中**(音の設計と音量バランス調整に手間。ミュートトグルは必須)

### ⑫ 勝利確率バー(または「試合の熱量」メーター)を中継パネルに常設

① スコア差・イニング・アウト・走者から簡易な勝利確率を計算し(精密さは不要、テーブル引きで十分)、スコアバグ直下に**横1本のバー**で両チームの確率を表示。打席ごとに数値がアニメーションで動く。大きく振れた打席には「!」マークを付ける。
② ESPN の Win Probability と同じ狙い。「65%→30%」という**振れ幅が、その一球の重大さを言葉より正確に伝える**。同点9回裏と5点差7回の違いが、スコアを読み解かなくても直感で分かるようになる。試合後に「今日の最大の分岐点」として1打席を名指しできるおまけ付き。
③ **中**(確率テーブルの用意。厳密なモデルは不要)

### ⑬ イニング終了時の「ダイジェスト行」を強化する

① 既存の `end` イベントを拡張し、「5回表終了 / ○○ 2点 / 通算 3-1 / 残塁2」のように**そのイニングの要約を1枚のミニカード**にする。得点イニングは琥珀の枠、無得点は控えめに。
② 現状の `end` は右寄せの小さいグレー文字で、**流れる情報の中に埋もれている**。イニングごとに区切りの要約が入ると、速いスピードで飛ばしている時でも試合の流れを追える。「経過」タブを持つスポナビの構造を1画面に圧縮した形。
③ **小**

### ⑭ 中継パネルをタブ化する(速報 / 経過 / 成績)

① 現状の1画面積み上げを、スポナビ型の**3タブ**に分ける。スコアバグは3タブ共通でヘッダー固定。「速報」= ダイヤモンド+カウント+直近3行、「経過」= 全ログ、「成績」= その試合の打者・投手成績(打数・安打・打点、投球回・被安打・自責)。左右スワイプ対応。
② 375px幅ではスコアバグ・ダイヤモンド・ログ・ボタンを同時に置くと**ログの高さが168pxしか取れていない**(現CSS)。タブに分ければ、それぞれのビューが画面を全部使える。スポナビ・MLB・ESPNが例外なくタブ構造なのは、モバイルではこれが唯一の解だから。
③ **中**(既存要素の再配置 + タブ切替。成績集計はイベントから作る必要あり)

### ⑮ 順位表: 1列目固定 + 等幅数字 + 「首位との差」の視覚化

① 順位表テーブルに `position:sticky; left:0`(既に成績表では実装済みなので同じCSSを流用)、`font-variant-numeric: tabular-nums` を適用。ゲーム差の列は数字だけでなく**細い横バーの長さ**で差を表現。優勝チームは行全体に琥珀の左ボーダー、Bクラスは行を減光。
② データテーブル設計の定石そのまま。等幅数字は桁が縦に揃うので**比較が目の動きだけで済む**。ゲーム差のバーは、13.5 と 2.0 の差が数字を読む前に伝わる。「明るい色は本当に重要なシグナルにだけ」の原則により、優勝ラインだけを色で立てる。
③ **小**

### ⑯ 部門別5傑を「リーダーカード」化する(1位だけ別格の扱いに)

① 5傑の表示を、1位だけ**選手名を大きく・顔写真枠(またはイニシャル印判)・数値を琥珀の特大**で出し、2〜5位は1行の細いリストにする。部門ごとに横スクロールのカード列にして、375pxでは1枚+次カードの端が見える形。
② 現状は5人が等価に並んでいるが、**「首位打者は誰か」が最も知りたい情報**で、2〜5位は判断材料にすぎない。「主役/判断材料/補足」の3層分類の適用例。カードの端を見せることで横に続きがあることが伝わる(モバイルの定石)。
③ **小〜中**

### ⑰ 全選手詳細成績表のモバイル対応: 列プリセット + ソート + 検索

① `.stat-t` の `min-width:560px` 横スクロールはそのまま残しつつ、上に **[打撃/出塁/長打/守備]** の列プリセット切替を置き、モバイルでは表示列を5〜6列に絞る。ヘッダータップでソート(現在のソート列は琥珀の▲▼で明示)。選手名の絞り込み入力を1つ。
② 「モバイルでは列を絞る / 横スクロール+固定は最後の手段」がテーブル設計の定石。現状は全列を常に出しているので、**ユーザーが自分で目的の列を探す作業**が発生している。プリセットは「今なにを見たいか」を先に聞く形にすることでそれを消す。ソートは順位表と成績表を1つに統合する効果もある。
③ **中**

### ⑱ 記録達成の「号外」自動生成(テロップ→紙面の二段構え)

① 中継中およびペナント進行中に達成条件を監視(サイクル安打、1試合4本塁打、ノーヒッター、20勝、シーズン本塁打記録更新、連勝記録など)。達成時は **中継画面に金枠テロップ** → 試合後に**新聞号外の紙面**を自動生成(既存の `paper-bg` 記念紙面プレビューの仕組みを流用)。ダウンロード/共有可能に。
② 放送の記録達成テロップの再現であり、かつ**このゲームにしかない見せ場**になる。新聞紙面という既存の世界観と完全に噛み合う上に、生成された紙面はSNSに貼れる = 拡散の種になる。既に `paper-bg` と QRコード生成が実装済みなので土台がある。
③ **中**(達成判定ロジックが本体。紙面生成は既存機構の再利用)

### ⑲ 貯金推移グラフと事件簿を「同じ時間軸」で連動させる

① 貯金推移グラフの折れ線上に、事件簿の出来事(故障、トレード、連勝ストップなど)を**マーカーとして打つ**。マーカーをタップすると該当の事件テキストがポップする。逆に事件簿の行をタップするとグラフの該当位置がハイライトされる。
② 現状は「グラフ」と「事件簿」が別セクションにあり、**因果が読者の頭の中でしか繋がらない**。同じ時間軸に乗せると「6月に急降下しているのはエースの離脱か」という物語が読み取れる。数字を物語に変える最も安上がりな方法。
③ **中**(グラフに日付軸のマーカーを載せる実装)

### ⑳ 全画面に「主役 / 判断材料 / 補足」の3層ルールを適用し、文字サイズと色を統一する

① 全画面の要素を機械的に3層に分類し、**層ごとに文字サイズ・色・太さを固定**する。主役(スコア、順位、達成記録)= 特大・琥珀または朱、判断材料(打者名、ゲーム差、部門1位)= 標準・生成り、補足(注釈、単位、日付、凡例)= 小・減光グレー。既存のCSS変数に `--t1/--t2/--t3` を足して全画面で使い回す。中間サイズの乱立を禁止する。
② これが**最大の課題「情報が多いが優先順位が付いていない」への直接の回答**。「全部目立たせて」は「全部目立たない」と同義であり、同じサイズで複数が主張すると読者は視線の置き場を失う。逆に、層さえ決めれば文字サイズと配置は自動的に決まるので、今後の画面追加でも迷わなくなる。バーで見ても読めるかという放送の合格ラインを、375pxに置き換えて全画面で検査する。
③ **中**(判断作業が本体。実装はCSS変数の置換)

## 4. 優先順位の推奨

**まず着手すべき3つ**(効果 ÷ コストが最大):
1. **⑧ 可変ウェイト** — setIntervalの置換だけで「見ている感」が跳ね上がる
2. **① B-S-Oカウント + ② スコアバグ統合** — 中継の骨格。ここが入ると他の演出が全部乗る土台になる
3. **⑳ 3層ルール** — 課題「優先順位が付いていない」への根本対処。他の19案の判断基準にもなる
